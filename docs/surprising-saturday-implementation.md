# Surprising Saturday implementation

## Server control

Main stays online. Compose creates one `surprising-saturday` container but does not start it. The `event-controller` service reads the desired state from `GET /api/internal/velocity/event-control` every three seconds. It checks the Docker Compose labels before it starts or stops the named event container. The controller has Docker socket access. Keep this service on the private Compose network and restrict access to its image and configuration.

The desired state starts 15 minutes before the event start time and ends at the event end time. A committee member can set an override in Admin → Servers. On starts the server for testing. Off requests a stop. Follow event schedule clears the override. The override stays in SQLite after an API restart.

During the 15-minute warmup, Velocity routes new players to main and the API rejects committee moves to the event server. At the event start time, the API changes the route revision once. Velocity then moves online players to the event server if it is healthy. A first-time player joins main. The API stores each player's preferred and last connected server in SQLite. Velocity reads the preference during login and reports each successful connection to the API. A returning player joins the preferred server when it is open and healthy. If main is down during a live event, Velocity can connect the player directly to the event server. A later event-server restart does not change the route revision or move the group again. When the event ends or the committee turns the server off, Velocity moves players to main. The controller waits until Velocity reports no players on the event server. It then waits five more seconds and sends a graceful Docker stop. If Velocity does not report live state, the controller keeps the event server running.

When a committee member turns the server on for testing, the committee can set a player's server choice from Admin → Servers until warmup begins. During a live event, players can set their choice on the event page while online or offline. The API checks the signed-in player's Minecraft UUID, ban state, and event time. It saves the choice even when the target server is starting. Velocity moves an online player when the target is healthy or routes them on their next login. A route revision change clears old pending moves.

The API writes `data/api/event-control.json` after an event or override change and when the schedule crosses a start or end time. It replaces the file atomically. The event controller reads this file and starts the event container before it contacts the API. It uses a fresh API response before it stops the container. The controller has no API startup dependency. During a deployment, the script recreates and starts an active event container before it restarts the API and main server. Velocity clears its update flag when the active route is healthy. A live event route needs the event server, not the main server.

Velocity checks website accounts, bans, and timeouts before it connects players to either Minecraft server. The event server has no local whitelist. Its backend port stays private, and FabricProxy-Lite checks the forwarding secret.

## Event data

`surprising_saturday_events` stores the title, a plain-text short description, two Markdown descriptions, start and end times, scoring type, and completion targets as JSON. The public page shows the first long description before the event starts. It shows the second long description on the event detail page after the start. The live banner and past-event cards show the short description. This version accepts `list_completion`. Each target has a namespaced mob ID, display name, optional HTTP or HTTPS link, and a point value from 1 to 1000. Existing events with ID-only lists load with generated display names and one point per target.

`surprising_saturday_participants` records each player who reaches the event server. `surprising_saturday_completions` records the first accepted completion time for each player and mob ID. The API sums the points for completed targets and sorts players by that score. When scores tie, it puts the player who reached that score first ahead. The official leaderboard excludes committee members. A player can turn on a display toggle to see committee results with a clear notice that those results do not count. The page links each player name to that player's profile and shows their pronouns.

Committee members create, edit, and delete events in Admin → Surprising Saturday, including live and ended events. The form uses one row for each completion target. The website asks for two confirmations before it saves changes to a started event or deletes an event. Deletion also removes that event's participants and completions in one database transaction. Editing target points recalculates the visible score. Removing a target hides its old completions from the score. Editing event times can change live server routing. The API stores event times in SQLite. The public API hides the title and the second description before the start time. The Event tab shows an upcoming card, a live page, and past events when they exist. It uses the Knowledge page renderer and styles for Markdown and HTML descriptions. It sanitizes the HTML before it inserts it into the page.

The Kill Shift template fills the title, all three descriptions, and 90 one-point targets from the Killshift coverage list. It does not set event times or create an event. The committee sets and edits event times in the website form.

## Killshift image and API

The repository's Killshift source already targets Minecraft 26.3. The release workflow builds its JAR. It downloads pinned Fabric API, FabricProxy-Lite, Simple Voice Chat, Emotecraft, and Player Animation Library JARs from Modrinth and verifies each SHA-512 hash. The event image build runs the Minecraft base image in setup-only mode and saves the Fabric and game server files in the image. It also copies the mod JARs into `/mods`. The entry script copies the prepared server files into the persistent event world before it starts the server. The event world stays in `data/surprising-saturday`.

On a mob kill, Killshift writes the killer UUID, mob ID, and event time to a delivery outbox in the event world. It sends each kill to `POST /api/internal/surprising-saturday/list-completion`. The API stores the first kill of each listed mob for each player. Each new record adds that target's points. Unlisted mobs and repeated kills add no points. The API returns the current score and completed mob list with each live-event receipt. Killshift uses that receipt for the kill message. `GET /api/internal/surprising-saturday/score/:uuid` remains available for independent score reads. The mod does not store the score or completion list. The API compares the official top three before and after an accepted score. Killshift announces a changed top three once to all players. The message shows the player colors, role labels, scores, and gold, silver, and bronze places. Committee members do not count in the official top three. The outbox retries a pending kill after an API outage or a server restart. The production backup includes the API database snapshot. It does not include the event world or its outbox. On player join, Killshift reads `GET /api/internal/surprising-saturday/player-data/:uuid`. It refreshes the profile each minute. Chat shows the Minecraft username and role. The name tag shows the nickname and pronouns below the username. Committee members get gamemaster command level 2 after the API confirms their role. This level permits `/tp`. These calls use the internal bearer secret and do not use gRPC.

## Logs

Docker sends the event server and controller logs to its local log driver. Alloy discovers their Compose service labels and forwards both streams to Loki. The Technical Grafana dashboard has one log panel for each service. The event server uses the Minecraft multiline rule. Loki keeps production logs for 14 days; event results remain in SQLite.

## RAM during an event

Production keeps main running when the event server starts. Main has an 8 GiB maximum Java heap and a 9 GiB container ceiling because its persistent world stays online. The event server adds a 3 GiB heap, starting at 1 GiB, inside a 4 GiB container ceiling for the modded event world. The waiting room serves both destinations and up to 100 visitors with a 768 MiB heap and a 1.5 GiB container ceiling. Velocity has a 256 MiB heap and 512 MiB ceiling. The API has a 384 MiB Node heap and 640 MiB ceiling; the website has a 256 MiB Node heap and 512 MiB ceiling. The event controller has a 96 MiB ceiling. Backup, Prometheus, Grafana, and Loki each have a 512 MiB ceiling; Alloy has 256 MiB, cAdvisor 128 MiB, node-exporter 64 MiB, and nginx 64 MiB.

Starting the event adds its 4 GiB ceiling and 1 GiB soft reservation. It does not lower or transfer the main server's allocation. With every production service running, the configured container ceilings total about 18.7 GiB, while soft reservations total about 8.3 GiB. These are limits and scheduling hints, not measured usage or preallocated RAM. The production host's physical RAM is not specified here, so compare `free -h`, `docker stats`, and Grafana memory graphs during a test event before raising either player limit. If the host has less than 18.7 GiB, all containers cannot simultaneously reach their ceilings.

The 4 GiB development host uses 1 GiB maximum heaps for main and event, 384 MiB for the waiting room, 192 MiB for Velocity, and 192 MiB Node heaps for the API and website. The dev overlay uses soft reservations without per-container hard memory limits. Configure host swap before running both Minecraft servers, then check `free -h` and `swapon --show`. Swap gives the host room for bursts but cannot replace enough physical RAM for sustained event load.

## Limits in this draft

The profile label refreshes when a player joins; it does not update during a session after a website profile edit. The website supports one scoring type. This workspace did not run a Docker image build, so the setup-only layer and first container start still need a deployment check.
