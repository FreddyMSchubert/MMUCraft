# Surprising Saturday implementation

## Server control

Main stays online. Compose creates one `surprising-saturday` container but does not start it. The `event-controller` service reads the desired state from `GET /api/internal/velocity/event-control` every three seconds. It checks the Docker Compose labels before it starts or stops the named event container. The controller has Docker socket access. Keep this service on the private Compose network and restrict access to its image and configuration.

The desired state starts 15 minutes before the event start time and ends at the event end time. A committee member can set an override in Admin → Servers. On starts the server for testing. Off requests a stop. Follow event schedule clears the override. The override stays in SQLite after an API restart.

During the 15-minute warmup, Velocity routes players to main and the API rejects committee moves to the event server. At the event start time, the API changes the route revision once. Velocity then moves online players to the event server if it is healthy. A later event-server restart does not change the route revision or move the group again. Players who leave the event server after a crash go to main and can return through the event page when the server is healthy. When the event ends or the committee turns the server off, Velocity moves players to main. The controller waits until Velocity reports no players on the event server. It then waits five more seconds and sends a graceful Docker stop. If Velocity does not report live state, the controller keeps the event server running.

When a committee member turns the server on for testing, the committee can move any online player between the two servers from Admin → Servers until warmup begins. During a live event, players can use the event page to move between main and the event server. The API checks the signed-in player's Minecraft UUID, ban state, event time, and server health before it accepts a player move. Velocity sends each move during its next three-second sync. A route revision change clears old manual moves.

Velocity checks website accounts, bans, and timeouts before it connects players to either Minecraft server. The event server has no local whitelist. Its backend port stays private, and FabricProxy-Lite checks the forwarding secret.

## Event data

`surprising_saturday_events` stores the title, a plain-text short description, two Markdown descriptions, start and end times, scoring type, and completion targets as JSON. The public page shows the first long description before the event starts. It shows the second long description on the event detail page after the start. The live banner and past-event cards show the short description. This version accepts `list_completion`. Each target has a namespaced mob ID, display name, optional HTTP or HTTPS link, and a point value from 1 to 1000. Existing events with ID-only lists load with generated display names and one point per target.

`surprising_saturday_participants` records each player who reaches the event server. `surprising_saturday_completions` records the first accepted completion time for each player and mob ID. The API sums the points for completed targets and sorts players by that score. When scores tie, it puts the player who reached that score first ahead. The official leaderboard excludes committee members. A player can turn on a display toggle to see committee results with a clear notice that those results do not count. The page links each player name to that player's profile and shows their pronouns.

Committee members create, edit, and delete events in Admin → Surprising Saturday, including live and ended events. The form uses one row for each completion target. The website asks for two confirmations before it saves changes to a started event or deletes an event. Deletion also removes that event's participants and completions in one database transaction. Editing target points recalculates the visible score. Removing a target hides its old completions from the score. Editing event times can change live server routing. The API stores event times in SQLite. The public API hides the title and the second description before the start time. The Event tab shows an upcoming card, a live page, and past events when they exist. It uses the Knowledge page renderer and styles for Markdown and HTML descriptions. It sanitizes the HTML before it inserts it into the page.

The Kill Shift template fills the title, all three descriptions, and 90 one-point targets from the Killshift coverage list. It does not set event times or create an event. The committee sets and edits event times in the website form.

## Killshift image and API

The repository's Killshift source already targets Minecraft 26.3. The release workflow builds its JAR. It downloads pinned Fabric API, FabricProxy-Lite, and Simple Voice Chat JARs from Modrinth and verifies each SHA-512 hash. The event image build runs the Minecraft base image in setup-only mode and saves the Fabric and game server files in the image. It also copies the mod JARs into `/mods`. The entry script copies the prepared server files into the persistent event world before it starts the server. The event world stays in `data/surprising-saturday`.

On a mob kill, Killshift writes the killer UUID, mob ID, and event time to a delivery outbox in the event world. It sends each kill to `POST /api/internal/surprising-saturday/list-completion`. The API accepts only IDs in the event list and stores the first kill for each player and mob ID in SQLite. Each new record adds that target's points. A repeated kill or a retried report adds no points. The mod does not store the score or completion list. After the API replies, Killshift reads `GET /api/internal/surprising-saturday/score/:uuid` and tells the killer their score and scored mobs. The API compares the official top three before and after an accepted score. Killshift announces a changed top three once to all players. The message shows the player colors, role labels, scores, and gold, silver, and bronze places. Committee members do not count in the official top three. The outbox retries a pending kill after an API outage or a server restart. The production backup includes the API database snapshot. It does not include the event world or its outbox. On player join, Killshift reads `GET /api/internal/surprising-saturday/player-data/:uuid`. It refreshes the profile each minute. Chat shows the Minecraft username and role. The name tag shows the nickname and pronouns below the username. Committee members get gamemaster command level 2 after the API confirms their role. This level permits `/tp`. These calls use the internal bearer secret and do not use gRPC.

## Logs

Docker sends the event server and controller logs to its local log driver. Alloy discovers their Compose service labels and forwards both streams to Loki. The Technical Grafana dashboard has one log panel for each service. The event server uses the Minecraft multiline rule. Loki keeps production logs for 14 days; event results remain in SQLite.

The dev Compose overlay sets a 1 GiB maximum Java heap for each Minecraft server. It starts each heap at 256 MiB. Each server has a 1.5 GiB container memory limit. Dev Velocity uses a 192 MiB heap inside a 384 MiB container limit. The dev API and website each have a 192 MiB Node heap inside a 384 MiB container limit. Production sets an 8 GiB main heap in a 9 GiB container and a 3 GiB event heap in a 4 GiB container. The event heap starts at 1 GiB. A container limit is a ceiling, not memory in constant use.

The dev container limits can add up to more than the VM's 4 GiB of RAM. These limits do not reserve RAM. Configure swap on the dev host before you run both Minecraft servers. The Compose swap limits permit use of host swap but do not create it. Check host RAM and swap with `free -h` and `swapon --show` after deployment.

## Limits in this draft

The profile label refreshes when a player joins; it does not update during a session after a website profile edit. The website supports one scoring type. This workspace did not run a Docker image build, so the setup-only layer and first container start still need a deployment check.
